## Evidence standard

The report separates direct facts, worker claims, and interpretation. A worker being created, `ready`, `running`, `done`, or self-reporting success does not establish useful completion. Strong outcome evidence is, in descending order: accepted/pushed/pinned source or installed artifact with exact identity and composed E2E; supervisor-reviewed commit/diff with required checks; task/runtime logs showing a task-relevant diff, command result, or concrete diagnosis; worker response text; lifecycle/status projection alone.

Each model/settings conclusion should identify:

1. the exact model, template/profile, reasoning effort, backend/runtime, and environment when recoverable;
2. the task or thread, its primary work type, any secondary work phases, and what the worker was asked to do;
3. what it actually produced, including no-output or wrong-output cases;
4. tests, review, promotion, live proof, reopen/steering, and human or stronger-model intervention;
5. confounders such as broken worktree materialization, tool-router failure, stale base, resource exhaustion, missing credentials, or prompt ambiguity.

Work types are classified as implementation, architecture/design, planning/source mapping, review/audit, debugging/diagnosis, verification/E2E, documentation, supervision/orchestration, or operational safety/scope adherence. A mixed run gets one primary type plus its material secondary phases; performance comparisons are grouped by work type before cross-type conclusions are drawn.

### Confidence rubric

Each percentage estimates how certain this report is that the **stated conclusion is supported by the audited one-month record**. It is not a future task success probability, benchmark score, or model win rate. The calibration considers source provenance, number and independence of cases, exact counterexample or acceptance evidence, review convergence, and unresolved infrastructure/prompt confounders.

Confidence is conclusion-specific. The report can be highly certain that a model found a particular defect while having much lower confidence that the same model is “best” overall, because exposure, task selection, and false-positive/false-negative denominators are not controlled.

- **95–100%:** direct and independently corroborated exact evidence; little material ambiguity.
- **85–94%:** multiple strong cases or an exact reviewed case, with limited generalization risk.
- **70–84%:** useful evidence but a smaller sample, mixed outcomes, or notable confounders.
- **50–69%:** sparse or mostly candidate-level evidence; only a narrow characterization is justified.
- **Below 50%:** execution evidence is insufficient for a meaningful performance characterization. A low number can accompany a highly certain fact such as “the backend rejected the model before it ran.”

Confidence that the record establishes any solo first/second/third order remains only **35%**.

**Implementation.** Terra High produced the strongest observed complex, acceptance-backed record, but unequal task assignment prevents a general implementation leaderboard. Current Spark Low is directly supported for tightly frozen metadata-only implementation: 19 accepted module changes plus a full aggregate build. Terra Max adds one independently accepted Thread 42 pin/proof candidate, still held behind the real browser gate. GPT-5.5 High and xhigh moved hard artifacts substantially without closing their defining gates. Opus was technically strong but unsafe in the audited shared-runtime run.

**Architecture/design and source mapping.** Sol XHigh and Fable produced the clearest observed role-specific evidence, not enough evidence for an ordinal comparison between them. Sol XHigh traced cross-module ownership and failure mechanisms to exact source boundaries; Fable repeatedly challenged package, wire, source, and supply-chain contracts. Mini and Luna Low were useful when the desired result was a narrow owner map or precise infrastructure diagnosis rather than a broad design.

**Review/audit.** Sol Max produced the strongest observed adversarial evidence on stateful runtime and exact-contract behavior, but its 138 of 594 rows still make this an exposure-qualified conclusion rather than an overall rank. Luna Max has repeated exact Thread 31 review rounds covering convergence, duplicate identity, capacity, and active-reference semantics. **Debugging/diagnosis.** Sol XHigh's EOF/restart analysis, Luna Low's branch-occupancy diagnosis, GPT-5.5's release selftest isolation, and Opus's CPython generator diagnosis were all useful. The Opus case is the reminder that a correct diagnosis does not compensate for unsafe execution behavior.

That supports Fable as the first model to trial for another audit, but one case cannot establish second or third place or a stable solo winner.

### Setting and sandbox effects

- `workspace-write` was enough for source edits but not standalone-clone Git metadata or ephemeral socket tests in several lanes. Thread 31's first direct Spark attempt stopped because linked Git metadata was mounted read-only; the changed mechanism then executed. Explicit `danger-full-access` made some integration gates possible, but the Opus incident demonstrates why broad shared-runtime authority is not a harmless performance setting.
- Current template verbosity was generally medium and reasoning summaries `auto`; no evidence supports attributing outcome differences to verbosity or summary mode.
- Quota boundaries affected whole provider accounts: Luna Max, GPT-5.5 High, and later Sol XHigh attempts stopped before useful execution, while Sonnet or Fable completed changed-provider work. Capacity diversity across providers was operationally valuable.
- A stopped/failed/listed Worker was often not the real execution state. The GPT-5.4 top-header commit, Fable readiness race, late Luna patch, Thread 27 reviewer verdict, the still-`running` Thread 193 row after terminal promotion, and multiple stale rows all required logs/worktree/session evidence beyond the projection.
- Model escalation without changing task shape was unreliable. The productive escalations changed at least one of: role, mechanism, work unit, reviewer identity, sandbox, or provider.

## Evidence limitations and unknowns

- This is an evidence review, not a randomized benchmark. Models received different task difficulty, prompts, repositories, sandboxes, quotas, and verification budgets. Cross-model comparisons are strongest within the same candidate/review pair and weaker across unrelated projects.
- Exposure remains unbalanced, although less extremely than in the prior snapshot. Sol Max occupies 138 of 594 rows (23.2%), Fable High 75 (12.6%), Spark Low 59 (9.9%), Terra High 56 (9.4%), Luna Max 15 (2.5%), and Terra Max six (1.0%). Rows are not trials; repeated identities, failed materialization, active work, and unequal task selection create substantial opportunity and selection bias. The data is compatible with genuine Sol Max strength and some benefit from being the most-used exact setting.
- The audit has no systematic false-positive, false-negative, cost, latency, or equal-prompt denominator for reviewers. It records material findings that led to repair and accepted outcomes, but cannot estimate precision, recall, or an overall review win rate.
- The month does not have one stable run ledger. June direct-worker identities, current Bus Worker rows, saved Codex rollouts, Tasks, Threads, and memos overlap but do not share a universal run id. The report therefore avoids a fabricated global success percentage.
- Historical June reasoning effort is frequently absent. Current template defaults are not backfilled onto those runs. GPT-5.5 xhigh and some GPT-5.4/GPT-5.5 examples are direct Codex sessions, explicitly labeled rather than silently treated as present catalog templates.
- Current Worker projections are live and mutable. They reached 594 rows at the frozen cutoff and contain stale `running`, disappeared worktrees, late patches, repeated identities, and lifecycle errors. Status counts describe the substrate, not the models.
- Provider quota, unsupported-model responses, Repos materialization, wrong repository id, dirty worktrees, missing runtime refs, process-group identity, socket/Git sandbox denial, and App Server reachability are separated from model reasoning whenever the model did not execute or the decisive failure was external.
- Memos sometimes summarize the same run for several hours. Mention counts are not run counts. Conversely, current Task/Worker registries omit some older June evidence, so absence from the live list is not absence of use.
- “Accepted source” is weaker than installed/live/composed acceptance. QEMU and browser work often reached reviewed source while the defining runtime/browser gate remained open; the report preserves that distinction.
- Token/cost/latency efficiency cannot be compared responsibly. Some current Worker rows expose goal-usage counters, but the meaning and coverage are not uniform across providers, direct sessions, resumed turns, or historical runs.
- Several July 16 results remain partial at the cutoff. Thread 31 has accepted/replayed Increment A source but zero composed routing E2Es. Thread 42 has an accepted current-target pin candidate and deterministic admission but Gate 2 remains `0/1`. Thread 187 reached source promotion and binary installation, but the loaded-service same-PID forced-drop proof cannot be exercised through a supported surface. Thread 199 has architecture evidence but no implementation diff. The report does not project any of those missing gates forward as completed.
- The independent Fable audit inspected prior committed draft `c7ba8a4`, whose evidence cutoff was 20:17 UTC. It did not review this revision's later Thread 42, 187, 199, registry, testing-gap, or reusable-prompt additions; those updates were checked directly against their primary records in this refinement.
- No external facts or network research were needed. The primary source review was read-only. The operator-authorized follow-up created and closed only the dedicated Fable audit Task/Workers; it did not edit Bus Threads, product code, services, or memos. This refinement otherwise changes only this documentation report and its isolated docs-repository branch/commit.
