## Findings

### [1] (high)
Q1 ANSWERED: Unaligned atomic accesses trap DETERMINISTICALLY — this is spec-mandated, not implementation-defined. The threads proposal states "Unlike normal memory accesses, misaligned atomic accesses trap" and the formal execution rule is "If both ord is SEQCST and ea modulo N/8 is not equal to 0, then: Trap" (checked before the bounds check). V8's message-template maps this trap to the exact observed error string "operation does not support unaligned accesses", confirming the QEMU wasm64 backend is hitting required behavior that no conforming engine can relax. Citation must come from the threads proposal render (webassembly.github.io/threads/core/), not the WebAssembly 3.0 core instructions page, which contains zero atomic instructions.

Evidence: Merges claims [0], [6], [20]. Overview.md verbatim: "Unlike normal memory accesses, misaligned atomic accesses trap. For non-atomic accesses on shared linear memory, misaligned accesses do not trap." Formal rule in WebAssembly/threads document/core/exec/instructions.rst: deterministic Trap on seqcst access with ea mod N/8 != 0. Verifier grep of the 3.0 core instructions page found 0 occurrences of 'atomic'/'shared'/'seqcst', while the threads overlay page has 85 occurrences of 'atomic'. V8 src/common/message-template.h defines WasmTrapUnalignedAccess with the exact reported message.

### [2] (high)
Q1 corollary: The alignment immediate on every atomic instruction MUST equal natural alignment or the module fails validation — a TCG backend cannot dodge the trap by encoding a smaller alignment hint. The only spec-compliant options are (i) dynamically proving alignment before the atomic (strategy a's checked fast path) or (ii) avoiding atomics entirely on the unaligned path (strategies a-fallback/b/c). V8's titzer confirms the design intent: engines "have to dynamically disallow" unaligned atomics because unaligned atomicity is infeasible on today's hardware; V8 emits an alignment check for every atomic access.

Evidence: Merges claims [8], [21]. Overview.md: "It is a validation error if the alignment field of the memory access immediate has any other value than the natural alignment for that access size." titzer (2019, verified verbatim via GitHub API): "since we can't statically disallow them, we have to dynamically disallow them"; "We also emit an alignment check for atomic accesses." Note: the 2019 hardware rationale is partially dated (ARMv8.4 FEAT_LSE2 handles some unaligned atomics), but the same thread confirms the spec trap requirement stands regardless.

### [3] (high)
Design lineage: the aligned-only-atomics rule descends from the TC39 shared-memory model that wasm threads is based on — lock-free atomicity forces natural alignment on ARM/MIPS/Power, and DataView atomics were excluded precisely because DataView is frequently unaligned. This is why the trap can never be engineered away at the engine level.

Evidence: Claim [3], verified verbatim: "On most systems (ARM, MIPS, Power), the need for lock-free atomic accesses will force a four-byte alignment... even if the system can handle unaligned non-atomic accesses"; "DataView objects are frequently accessed at unaligned addresses while atomic accesses must be aligned on most platforms." Wasm lineage confirmed by threads spec relaxed-memory chapter: "WebAssembly's relaxed memory model is heavily based on those of C/C++11 and JavaScript." Note: tc39 GitHub is outside the requested source allowlist; re-cite via ECMA-262 clause 29 in any published doc.

### [4] (high)
Q2 part 1 ANSWERED: Misaligned NON-atomic loads/stores on shared linear memory are fully defined, never trap, and "must succeed regardless of the annotation" — the memarg alignment field is only a performance hint ("expected alignment"), with no runtime alignment semantics. A misalignment-trapping mode was explicitly rejected as the spec default because it "would incur some runtime cost for branching on most platforms." This makes strategy (a)'s byte-wise fallback, strategy (b)'s two-halves stores, and strategy (c)'s helper-implemented byte stores all legal, trap-free wasm at any in-bounds address, and it quantifies (qualitatively) the per-store branch cost strategy (a) pays.

Evidence: Merges claims [1], [7], [14], [20]-nonatomic-half. Core spec exec note: "Unaligned access violating that property is still allowed and must succeed regardless of the annotation. However, it may be substantially slower on some hardware." Overview.md: "For non-atomic accesses on shared linear memory, misaligned accesses do not trap." Rationale.md: opt-in 'debug mode' trapping "isn't the specified default" due to branch cost. Caveat: no-trap does not imply atomicity — racing readers may observe torn values (see tearing finding).

### [5] (high)
Q2 part 2 ANSWERED (race semantics): Data races between non-atomic accesses on shared memory are permitted and DEFINED — "there is no undefined behaviour"; effects are bounded to the union of the racing accesses' byte ranges, and a read's value is composed per-byte from write events (ComposeWriteEventBytes). Tear-freedom ([[NoTear]]) applies ONLY to naturally aligned, equal-memory-range integer accesses; per the wasm memory model (Conrad Watt, model co-author, plus the formal tearing predicate: notears iff ea mod N/8 = 0 AND N <= 32), naturally aligned non-atomic i32/i16/i8 loads and stores will not tear, but unaligned accesses, aligned non-atomic i64 accesses, and any different-size race (e.g., a byte-wise or two-halves split store racing a full-width read) can be observed as a torn mix of bytes from different writes. Consequence for the backend: an I/O worker racing a split store sees a defined but possibly partially-committed value — never UB, never corruption outside the written bytes; and 64-bit guest stores must use two aligned 32-bit halves or an aligned atomic, because even an aligned plain i64 store may tear.

Evidence: Merges claims [4], [10], [12], [16], [22]. ECMA-262 §29: "The memory model defines... the possible values read from data races. To wit, there is no undefined behaviour"; §29.7.3 Tear Free Reads asserts [[NoTear]] implies ByteIndex mod ElementSize = 0 and applies only to equal ranges. DISCUSSION.md: "the bytes affected by a race are limited to the union of the byte ranges accessed by the racing accesses." Watt in threads#199 (verified via GitHub API): "Yes, naturally aligned i32 loads and stores won't tear"; formal tearing(iN', N, ea)=notears iff aligned AND N<=32, so aligned non-atomic i64 TEARS. MDN: predictable racing requires "the operations that race all have the same access size."

### [6] (high)
Q3 part 1 ANSWERED (available orderings): The JS/wasm shared-memory model exposes exactly TWO ordering strengths — sequentially consistent (atomic) and unordered (non-atomic). "No orderings weaker than sequentially consistent and stronger than unordered, such as release-acquire, are supported" (ECMA-262 §29.1), and "Currently all atomic memory access instructions are sequentially consistent" (threads Overview). atomic.fence is a seqcst-strength barrier that, uniquely among atomic operators, "does not target a particular linear memory," so it is available as a whole-memory publication barrier. Therefore any split-store publication scheme MUST use seqcst primitives (or host synchronization like postMessage) — there is no cheaper release/acquire tier to reach for; weaker orderings exist only in the unshipped shared-everything-threads draft.

Evidence: Merges claims [2], [5], [11], [15]. ECMA-262 §29.1 verbatim on the two orderings and explicit exclusion of release-acquire; threads spec: "The atomic.fence instruction... is intended to preserve the synchronization guarantees of the fence operators of higher-level languages. Unlike other atomic operators, it does not target a particular linear memory"; MDN: "JavaScript does not provide operations with other ordering guarantees." DISCUSSION.md confirms weaker atomics were deliberately deferred despite known performance value.

### [7] (high)
Q3 part 2 ANSWERED (exact publication protocol): A synchronizes-with edge between memory events is created ONLY when a seqcst read reads-from a seqcst write with an EQUAL memory range (ECMA-262 §29.6.5; wasm threads model equivalently fixes an atomic read reading a same-width atomic write before it in happens-before). The correct split-store publication protocol is therefore: (1) perform the non-atomic byte/half writes, (2) execute a seqcst atomic store to a flag/sequence location (optionally preceded by atomic.fence), (3) the consumer performs a MATCHING seqcst read of the same address and size; happens-before plus the Coherent Reads constraint (§29.7.2) then forces all earlier plain bytes to be visible. Critical negative results: a fence alone creates no edge for a plain-reading agent, and a writer-side seqcst store alone gives a plain reader nothing — the reader-side seqcst access is mandatory. This is the strongest (and only) cross-agent guarantee available, and it fully protects I/O-reader workers at protocol boundaries.

Evidence: Merges claims [9], [13], plus the verified scope caveats on [2]. §29.6.5 verbatim: "writeEvent synchronizes-with readEvent... if readEvent reads-from writeEvent..., readEvent.[[Order]] is seq-cst, writeEvent.[[Order]] is seq-cst, and readEvent and writeEvent have equal memory ranges"; Note 3 confirms equal-range exclusivity. §29.6.6 happens-before = transitive closure of agent-order ∪ synchronizes-with; §29.7.2 then mandates visibility of agent-order-prior plain writes. Verifier caveat on [2]/[9] made explicit here: fence availability is not fence sufficiency; the observing agent must use paired atomic accesses.

### [8] (medium)
Q4 partially ANSWERED (engine/host documentation): (i) V8 emits a dynamic alignment check for every atomic access and its unaligned-atomic trap message is exactly the observed RuntimeError text (src/common/message-template.h WasmTrapUnalignedAccess). (ii) The spec-level rationale for not trapping unaligned plain accesses is the per-access branch cost "on most platforms", and the core spec warns unaligned plain access "may be substantially slower on some hardware" — the only cost statements that survived; no quantified V8/SpiderMonkey unaligned-cost documentation survived verification. (iii) Host-model guidance: Atomics.store "guarantees that the write is tear-free, and that all atomic writes are sequentially consistent"; SharedArrayBuffer updates become visible to other agents only "eventually" and "to synchronize, atomic operations are needed"; and MDN/ECMA-262 Shared Memory Guidelines recommend "ensure that different memory cells are used by atomic and non-atomic operations and that atomic accesses of different sizes are not used to access the same cells at the same time" — strategy (a)'s atomic-fast-path-plus-plain-fallback on the SAME racing guest cells is exactly the pattern this predictability guidance warns against.

Evidence: Merges claims [17], [18], [19], engine parts of [6]/[21], cost parts of [14]. All MDN quotes verified verbatim and corroborated by primary ECMA-262 §29 text (the mixing guideline is lifted nearly verbatim from the normative spec's Shared Memory Guidelines). Marked medium because the visibility/guidance claims rest on secondary MDN pages (though ECMA-corroborated) and no firefox-source-docs or quantified engine-cost source survived; the V8 alignment-check fact is from a maintainer comment plus source inspection, not formal engine docs.

### [9] (high)
STRATEGY MAPPING AND RECOMMENDATION for a single-guest-vCPU worker where other workers only READ guest memory for I/O. Strategy (a) alignment-checked atomic fast path + byte-wise fallback: LEGAL and workable — the dynamic check is mandatory anyway (validation forbids under-aligned hints; the trap is unavoidable) — but pays a per-store branch, and its atomic-vs-plain mixing on the same racing cells is the exact pattern the ECMA/MDN guidelines warn reduces predictability; its byte-wise fallback is torn-visible to readers regardless. Strategy (b) two-halves non-atomic stores 'published with fences': the stores are legal and each naturally-aligned <=32-bit half is individually tear-free, but the premise is UNSOUND as stated — fences alone create no synchronizes-with edge for racing plain readers, so (b) cannot deliver store atomicity to observers; it degenerates to (a)-fallback semantics plus wasted fences unless paired with the seqcst flag protocol. Strategy (c) helper-call slow path for unaligned stores only: fully legal, trap-free, simplest codegen, keeps atomics entirely off the unaligned path; cost is a call per unaligned store, acceptable when unaligned guest stores are rare (typical for riscv64 guests). RECOMMENDATION: hybrid (a)+(c) with the atomic removed from the plain-store fast path — (1) dynamic alignment check; aligned <=32-bit guest stores commit as plain naturally-aligned stores (tear-free per the wasm model, and with one writer there is no write-write race); (2) aligned 64-bit stores commit as an aligned atomic store or two aligned 32-bit halves (a plain aligned i64 store may tear); (3) unaligned stores take the byte-wise/helper path (c); (4) guest atomics/AMOs use real wasm atomics behind the proven-alignment check (unaligned guest atomics can legitimately trap/fault per guest architecture); (5) cross-agent consistency for I/O-reader workers is provided at protocol boundaries — map guest barriers/doorbell writes to atomic.fence plus a seqcst flag store that I/O workers consume with a matching same-range seqcst read. Torn intermediate states of in-flight plain stores remain observable to a reader that polls raw guest memory without the seqcst handshake; that is defined-but-unordered behavior and must be excluded by the I/O protocol, not by per-store atomics.

Evidence: Synthesis of all confirmed findings: trap determinism + natural-alignment validation ([6],[8],[20],[21]) forces the alignment check or atomic avoidance; non-atomic legality ([1],[7],[14]) legalizes (b)/(c) and (a)'s fallback; tearing rules ([12],[16],[22]) give tear-freedom exactly to aligned <=32-bit plain stores and deny it to i64/unaligned/mixed-size; ordering/publication rules ([2],[5],[9],[11],[13],[15]) show seqcst pairing is the only cross-agent edge, invalidating fence-only (b); guidelines ([17]) disfavor atomic/plain mixing on racing cells. The single-writer premise (one guest vCPU) eliminates write-write races, making plain aligned stores sufficient for the fast path; only reader-visibility needs the seqcst protocol.

## How this applies to us

(1) Misaligned ATOMIC accesses in the WebAssembly threads spec deterministically trap by normative rule ("If both ord is SEQCST and ea modulo N/8 is not equal to 0, then: Trap"), and validation forbids encoding a sub-natural alignment hint on atomics — the observed V8 "operation does not support unaligned accesses" RuntimeError is required spec behavior, not an engine quirk, so no design may ever issue a wasm atomic to an unproven-alignment address. (2) Misaligned NON-atomic loads/stores on shared linear memory are fully permitted and must succeed; data races on shared memory are defined (no UB, effects bounded to the union of racing byte ranges), but tear-freedom holds only for naturally aligned, equal-range integer accesses of 32 bits or less — so byte-wise or two-halves stores (and even aligned non-atomic i64 stores) are legally observable torn by a racing reader. (3) The model offers exactly two orderings (seqcst and unordered — no acquire/release), and a synchronizes-with edge arises only when a seqcst read reads-from a seqcst write of EQUAL memory range; therefore a split store is published by following the plain writes with a seqcst flag/doorbell store that the consumer reads with a matching same-address, same-size seqcst read (atomic.fence is seqcst and memory-agnostic but by itself creates no edge for plain readers). Recommendation for a single-guest-vCPU worker with read-only I/O workers: a hybrid of (a)+(c) — dynamic alignment check; aligned stores commit via plain naturally-aligned stores (tear-free at ≤32 bits) or aligned atomics/two aligned 32-bit halves for 64-bit; unaligned stores take a byte-wise non-atomic or helper-call path; cross-agent consistency for I/O readers comes from a seqcst doorbell protocol at device-handoff points, mapping guest barriers to atomic.fence/seqcst accesses. Strategy (b)'s "fences publish the halves" premise is unsound as stated — fences alone give racing plain readers nothing; pure (a) with an atomic fast path is workable but per-store branch cost and MDN/ECMA guidance against mixing atomic and non-atomic access on the same racing cells favor keeping atomics off the plain-store commit path.

Design consequences for the wasm64 backend:
- NEVER emit a wasm atomic to an unproven-alignment address: the trap is
  normative (spec + validation forbid under-aligned hints); no engine can
  relax it. The current store-admission trap is required behavior.
- Strategy (b) "two halves + fences" is UNSOUND as stated: atomic.fence
  creates no synchronizes-with edge for plain readers; only a seqcst read
  reading a same-range seqcst write does.
- RECOMMENDED: hybrid (a)+(c). Dynamic alignment check; aligned <=32-bit
  stores commit as plain stores (tear-free when naturally aligned);
  unaligned (and 64-bit as needed) via byte-wise/two-halves plain stores or
  helper slow path; keep atomics OFF the plain-store commit path entirely.
- Cross-agent visibility for read-only I/O workers comes from a seqcst
  DOORBELL protocol at device-handoff points (guest barriers map to
  atomic.fence/seqcst accesses); between doorbells, torn intermediate
  states are unobservable to a correct consumer.
